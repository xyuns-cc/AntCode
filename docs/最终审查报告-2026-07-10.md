## 0. 严重度与「态」约定

- **P0**：live 且可造成跨租户/跨 worker 越权、数据损坏或直接远程代码注入。
- **P1**：高风险安全、数据丢失、生产不可用、真实并发错误或多副本失效。
- **P2**：明确的功能/性能/资源/多副本健壮性问题。
- **P3**：工程质量、死代码与可维护性风险。
- **态**：`live`=正常路径即可触发；`latent`=真实 bug 但当前无调用方或需特定部署形态；`hardening`=纵深加固。

## 1. 结论摘要

- 合计有效发现约 **60+** 项：P0 级 **9**、P1 级 **20+**、P2 级 **~25**、P3 级 **~15**。
- **底盘扎实**：此前 R1–R8 / T6 / T7 修过的安全项（登录限流+锁定、密钥轮换、子进程 env 双层脱敏、git URL 白名单、gateway 明文端口 fail-closed、Redis per-worker ACL、zip-slip 防护、XFF 受信代理白名单）经独立核对**真实且无绕过**。
- **两份报告高度互补**：
  - Codex 独占的关键补充：`task_logs` 表在新部署根本不创建、生产 Nginx/WS 代理配错、一次性凭据并发重放、长期 JWT 落 URL、禁用用户不立即失效、Artifact 事务不完整、固定路由被动态路由遮蔽、CI/类型检查门禁全面失效、**实测验证结果**。

## 7. 系统性主题（比单点更值得投入）

1. **分布式多副本正确性尚未真正达成**：master 的 `reconcile` 裸 update 绕 CAS（P0-7）、`lease_sweeper` 漏 leader gate、fencing token 只记日志不参与写入判定；gateway 的 `WatchControl` PEL 丢失 + `_event_id_map` 进程内。**单实例能跑，>1 副本会重复回收/重复派发/终态翻转/控制丢失。** 若近期不上多副本，应在文档明确「当前仅支持单 master / 单 gateway」。

2. **「进程内状态」在 `SERVER_WORKERS>1` 就破**：`worker_auth` 的 secret/nonce/限流、告警配置、gateway 限流计数。此前刚把 web_api 默认 workers 提到 2 又回退（见 git log `dda2226`/`b2497cb`），正说明这一类问题已实际踩中。凡「限流/去重/配置/计数」都应落 Redis。

3. **双实现与死代码是最大维护负债**：至少 6 对重复实现，「改一处忘另一处」是未来 bug 温床，且序列化两套里 bool 问题（P0-8）都在。发版前值得做一次死代码清扫。

4. **内存分页反模式**：多处 `.all()` 全量拉取后 Python 切片，中低数据量无碍，是随规模劣化的定时炸弹。

5. **质量门禁与回归基线缺失**（本合并新增强调）：Ruff/mypy/后端测试/前端构建当前均无法作为合并门禁，`task_logs` 这类「schema 与代码不一致」的问题正是因缺乏建表/迁移校验才潜伏至今。

## 11. 异步资源生命周期系统扫描（新增 P0×5 · P1×8 · P2×10）

### P0
